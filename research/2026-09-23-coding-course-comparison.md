# Coding-agent course comparison

**Question.** Does the proposed eight-section route split the lifecycle too finely, especially by putting cross-session work in section 7? This note compares publicly published, first-party curriculum information as accessed 2026-09-23. It evaluates *using agents to build software*, not curricula for building agent-powered applications.

### Name correction: DeepLearning.AI is related, but not *Claude Code in Action*

[DeepLearning.AI's *Claude Code: A Highly Agentic Coding Assistant*](https://www.deeplearning.ai/courses/claude-code-a-highly-agentic-coding-assistant) is a separate Anthropic-partnered short course, not the Anthropic Academy/Coursera course above. It is an intermediate, 10-video-lesson, two-hour course organized as codebase understanding; adding features; testing/debugging/refactoring; parallel features; GitHub integration/hooks; notebook-to-dashboard; and Figma/Playwright-MCP web work. It publishes a lesson inventory and three practice projects (RAG chatbot, ecommerce notebook/dashboard, Figma-based web app). It is useful counterevidence that an agent course can teach several SDLC activities through concrete projects rather than a lifecycle chapter inventory. It does **not** add a materially different lifecycle scope to the three-course comparison: it remains a Claude Code workflow course, and public copy does not establish delivery/operations practice beyond GitHub/hooks.

The [Fall 2025 page](https://themodernsoftware.dev/fall2025) also exposes only a high-level description in the retrieved content, but the instructor's repository has public assignments. [Week 6](https://github.com/mihail911/modern-software-dev-assignments/blob/master/week6/assignment.md) requires targeted security repairs and a rerun of checks. [Week 7](https://github.com/mihail911/modern-software-dev-assignments/blob/master/week7/assignment.md) requires implementation, manual review, tests, PRs, AI review and a reasoned comparison. This is stronger evidence than a marketing topic list: granular tool-led exercises can practice a coherent engineering capability. The tools are examples, not reasons for this course to require Semgrep or Graphite.

## Facts about the comparison

1. **Tool detail and lifecycle breadth can coexist, but are not the same axis.** Anthropic's course has concrete Claude Code controls and puts automation, verification and sharing in separate modules. Stanford is broad across the SDLC but names technology/practice areas rather than a published teaching sequence. AI Hero uses tool-specific examples yet places requirements, plans, feedback loops and autonomy in a staged engineering workflow.
2. **AI Hero makes the clearest explicit cross-session-to-lifecycle connection in the inspected sources.** Its cohort teaches context-window-sized decomposition, PRDs, tracer bullets and multi-phase plans in Week 1; tests, CI and quality enforcement in Week 2; and later autonomous issue/branch work. Its crash-course page separately calls out compaction versus handoff and session-sized chunks. That is evidence for a cross-session capability, but not evidence that it subsumes planning, testing or release practice.
3. **The inspected curricula do not establish operations depth comparable to every claim in the proposed advanced section.** Anthropic names cloud routines, headless execution and GitHub Action automation; Stanford names deployment as a goal and publishes security/review assignments; AI Hero names sandboxing, backlog work, branches and commits. Those inspected materials do not demonstrate a complete incident-response, monitoring, rollback or consumer-compatibility teaching route. This is a source limit, not a claim that no such material exists elsewhere.

## Comparison to the proposed eight sections

The proposal is described in [`2026-09-22-course-review-and-action-plan.md` §§Learning progression and material map](../2026-09-22-course-review-and-action-plan.md#learning-progression-and-material-map): 1 setup, 2 agent mechanics, 3 harness/context controls, 4 bounded everyday delivery, 5 steering/skills, 6 reliable execution, 7 cross-session shipping, 8 advanced harness/enterprise work. The active outline has different section numbers; this mapping uses the **proposed** numbers.

## Interpretation and recommendation

**Section 7 should be a coordination-and-continuation chapter, not an SDLC container.** Its before/after condition is simple: a learner can resume a known, scoped change in a fresh context, find the current decision and evidence, update the work plan after a requirement change, and avoid duplicating or losing work. The ticket exercise in the proposal can prove that. This is a real capability that neither a compact command lesson nor a one-session feature exercise proves.

**Section 7 should not own:**

- discovering/refining requirements or writing the first specification — section 4's bounded delivery and any earlier planning practice;
- agent/model/harness context mechanics — sections 2–3;
- reusable steering artifacts — section 5;
- selecting tests, diagnosing defects, code review, CI or evidence quality — section 6 and the recurring workflow in 4;
- deployment, release governance, production operations, consumer compatibility or incident response — section 8 only where the course has a concrete advanced exercise.

The wider boundary problem is not merely section count. The proposal labels 4 “everyday workflow,” 6 “reliable execution,” 7 “shipping,” and 8 “enterprise,” but planning, verification and review recur at every scale. If headings are treated as exclusive ownership, learners will get a false waterfall. Use sections as the *first explicit practice* and give each a unique observable exit condition; then reuse the same loop in later exercises.

**Strongest evidence against broadening section 7:** AI Hero, the closest public lifecycle source, teaches multi-session decomposition and handoffs alongside—not instead of—specification, multi-phase planning, feedback loops, test selection, CI and quality enforcement. Anthropic likewise has distinct public modules for steering, configuration, automation, and verification/share. Both structures argue that carrying work across sessions is a cross-cutting constraint on the lifecycle, not a reason to relocate the lifecycle into one late chapter.

**Counterargument.** The same AI Hero material joins PRDs, multi-phase plans, large features, feedback loops, AFK agents, issue backlogs and branches in one two-week program. A learner may experience them as one “shipping larger work” capability, and a course that artificially isolates them can feel fragmented. **Response:** join them through one repeated end-to-end exercise and cross-references, not by making section 7 the first home for essential specification/testing/review skills. The proposal already places those prerequisites earlier; preserve that order.

**Confidence and limits.** High confidence in the inspected titles, outcomes, topic lists and Stanford assignment requirements. Moderate confidence in the boundary inference: syllabi and marketing describe advertised scope, not learner performance. Stanford's current landing page lacks a detailed sequence; its earlier assignments are public. Anthropic and AI Hero lesson content is partially gated. No source supports measuring teaching effectiveness or this course's operational depth from these pages, and this review does not rank courses by popularity.
