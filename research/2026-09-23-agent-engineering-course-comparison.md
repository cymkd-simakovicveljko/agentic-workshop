# First-party agent-engineering course comparison

**Retrieved 2026-09-23.** This is a contrast sample, not a ranking or a claim about teaching effectiveness. It uses public, first-party course pages only. The proposed structure is in [the course review](../2026-09-22-course-review-and-action-plan.md#learning-progression-and-material-map); the active course remains different ([OUTLINE.md](../OUTLINE.md#sections)).

## Scope first: these courses solve a different problem

Our proposed course teaches **using a coding agent to change and verify ordinary software**: a learner manages context, instructions, repository state, evidence, handoffs and compatibility. The three comparison courses teach **building an AI/LLM-powered product or agent**. Their agent is the system being designed, evaluated and, sometimes, deployed—not the collaborator changing the learner's existing codebase. That distinction makes their operational material relevant as a capability check, not a model for copying topic counts.

### Three different things called “test”

The comparison makes one course boundary non-negotiable:

1. **Software tests** check application contracts—for example, the proposed blank-task repair and compatibility matrix in sections 6 and 8 ([review map](../2026-09-22-course-review-and-action-plan.md#learning-progression-and-material-map)).
2. **AI-system evaluation** measures variable model/agent behavior over representative inputs, metrics, judges, feedback, latency or cost. This is the subject of DeepLearning.AI Module 4, Hugging Face Bonus Unit 2, and FSDL LLMOps; it is not proven by a conventional application test.
3. **Learner assessment** checks whether a student met a course threshold: DeepLearning.AI quizzes/graded assignments and Hugging Face's benchmark-based certificate. A learner passing an assignment does not validate a deployed AI system; an AI system scoring well does not prove the learner can safely modify a repository.

Name this distinction without importing another course's topic inventory. Evaluating a coding-agent workflow is relevant even when the application being changed has no AI feature: active section 8 already discusses representative tasks, repeated trials and grader calibration. That differs from the application's regression tests and from deploying a new AI product.

## Capability check against all eight proposed sections

| Proposed section | Capability judgment from this comparison |
| --- | --- |
| 1. Getting started | **Keep.** Minimum permissions, baseline checks, diff review and a safe restart are coding-agent trust-boundary skills. The comparison courses' tool/platform onboarding is analogous only at a high level; none substitutes for reviewing a code change in an existing repository. |
| 2. How agents work | **Keep, but bound it.** Tool/message/context mechanics help learners predict a coding harness. Do not turn it into agent-product architecture. Add the three-way distinction above here or where section 6 first uses evidence. |
| 3. Working with OMP | **Keep as a prerequisite, not a taxonomy.** Context compaction, interruption and factual resumption are operational controls for a human-agent collaboration. Framework memory/state in Hugging Face is a different kind of state. |
| 4. Everyday workflow | **Keep as the practical core.** A small reversible change and observable acceptance sequence are the right transfer target. External courses support iterative work, but their prompts/workflows are product code rather than a change in an unfamiliar repository. |
| 5. Steering agents | **Keep.** Instructions, skills, source selection and near misses are governance of a coding agent. They should not be expanded into a survey of agent frameworks; Hugging Face explicitly says plain code may suffice for simple workflows. |
| 6. Reliable execution | **Keep.** Root-cause diagnosis, shared callers, recoverable work and mechanically checked standards teach conventional engineering evidence. Do not relabel these as AI evals. |
| 7. Shipping across sessions | **Retain only because it has a distinct, observable failure mode:** a fresh context must continue tickets after a requirement changes, reconcile dependencies, and preserve evidence ([proposed exercise](../2026-09-22-course-review-and-action-plan.md#learning-progression-and-material-map)). That is neither agent memory nor product deployment. Without that exercise, this is merely planning/recovery repeated from sections 3, 4 and 6 and should be folded back into them. |
| 8. Advanced harness design and enterprise work | **Keep as advanced depth.** The exporter seam, opt-in v2 and consumer matrix teach compatibility and rollout reasoning that the agent-product curricula do not replace. Do not add deployed-agent observability unless the course product changes to building an AI system for users. |

## Decision

**Recommendation: retain the eight outcome areas, including a distinct section 7, but do not imitate the comparison courses' topic inventory.** The external curricula support operational granularity when it corresponds to a different failure surface—evaluation, observability, deployment, or stateful orchestration. The proposed course already gives section 7 one: durable human work across fresh agent contexts and a changed requirement. It should remain an exercise-led capability, not a tool-specific “shipping” lecture or a tracker/framework survey.

**Strongest case for retaining operational granularity.** Software delivery with a coding agent has lifecycle state beyond a model interaction: repository state, evidence, unresolved decisions, ticket dependencies and requirement changes must survive a new conversation. Sections 3, 6, 7 and 8 separate context control, recovery/enforcement, cross-session continuity and consumer/rollout compatibility. Collapsing them hides which state failed and removes the chance to practice the corresponding recovery.

**Strongest case against it.** A heading count can fake progression. The comparison courses contain many narrow named topics because they teach an AI product's architecture, behavior measurement and production operation; not all belong in this course. If section 7 only makes learners resume from a factual handoff, without a larger dependency or changing-requirement problem, it duplicates planning in section 4, steering in section 5 and recovery in section 6. Workflow evaluation still belongs in the harness material, but an agent-product deployment curriculum would be a separate scope choice.

**Confidence and limits.** High confidence in the scope distinction and the public syllabus claims. Moderate confidence in the transfer recommendation: public outlines show advertised coverage, not teaching quality, completion rates, or every gated exercise. DeepLearning.AI's graded content is paywalled; FSDL flags its 2023 tooling as dated; neither limitation was worked around. No popularity ranking or effectiveness claim is made.
